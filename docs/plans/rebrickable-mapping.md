# Rebrickable to LDraw mapping

Users upload inventories in Rebrickable's CSV format. Rebrickable uses its own part numbers and colour ids; the toolkit and LDraw use part file numbers (`parts/<id>.dat`) and LDraw colour codes. Two committed data files bridge them:

- `ldraw_tools/data/rebrickable-colours.json`: Rebrickable colour id to LDraw colour code (`method`: override, name or rgb; `exact` flag; `unmapped` list).
- `ldraw_tools/data/rebrickable-parts.json`: Rebrickable part_num to LDraw part number, listed only where they differ (identity is the default), plus `notes` and a capped `no_ldraw` list.

Both are generated by `tools/build_rebrickable_maps.py` (deterministic, offline). Refresh:

```
# download and gunzip colors.csv, parts.csv, part_relationships.csv from
# https://cdn.rebrickable.com/media/downloads/<name>.csv.gz into RB_DIR;
# unpack complete.zip from https://library.ldraw.org/ and pass the "ldraw" folder
python3 tools/build_rebrickable_maps.py RB_DIR LDRAW_DIR          # rewrites both JSON files, prints the report
python3 tools/build_rebrickable_maps.py RB_DIR LDRAW_DIR --check  # CI-style: exit 1 if files would change
```

## Colours

The bulk `colors.csv` has no LDraw ids (columns id, name, rgb, is_trans, num_parts, num_sets, y1, y2; only the API carries external ids and it needs a key). Each colour is matched against `LDConfig.ldr` in this order:

1. `COLOUR_OVERRIDES` in the script (hand curated, `method: override`).
2. Normalised name (case, punctuation and `gray`/`grey` ignored; an override never lets a second Rebrickable colour take the same code by name).
3. Exact RGB with the same transparency, restricted to plain colour families (no rubber, Modulex, opal, glitter, speckle, chrome, pearl, metallic... unless the Rebrickable name says so). `method: rgb`.
4. Nearest RGB (redmean distance, same transparency and families) within `MAX_APPROX`; `exact: false`. Farther than that the colour stays unmapped.

Deviation from the brief: name comes before RGB. LDConfig re-valued many colours (Black is 1B2A34 there, 05131D at Rebrickable; transparent colours carry display-adjusted values), and RGB alone is ambiguous (Modulex White F4F4F4 equals plain White, Trans-Clear equals four LDraw clears), while names are stable. Rebrickable ids in this download also often equal the LDraw code, but that was not relied on: Reddish Brown is 70 in this file, Dark Purple is 85 but LDraw 85 is named Medium_Lilac (hence an override).

Coverage (275 Rebrickable colours, 4,736,100 part-colour uses in `num_parts`):

| | colours | weighted by num_parts |
|---|---|---|
| mapped | 237 | 99.74% |
| mapped and exact | 202 | 99.65% |
| unmapped | 38 | 0.26% |

All 82 colours with num_parts >= 1000 are mapped except `9999` [No Color/Any Color] (10,976 uses), which is deliberately left unmapped because it means "any colour" and the consumer should decide; 81 mapped, 80 exact. `-1` [Unknown] is unmapped for the same reason. Methods: name 185, rgb 46, override 6.

Approximate colours worth knowing (exact=false): Vibrant Yellow 1062 to Yellow 14 (2,270 uses, no LDraw equivalent), Pastel Blue 1051 to Medium_Azure 322, Trans-Medium Purple 1094 to 44, Pearl Sand Blue 137 to Sand_Blue 379, Flat Dark Gold 178 to Nougat 92, Trans-Light Royal Blue 1006 to 39, Metal 1135 to Cool_Silver 296, plus a tail of Duplo, HO, Clikits, Vintage and Two-tone colours (under 50 uses each). Run the script for the full list.

Caveats that could not be verified without the Rebrickable API:
- Name matches are trusted even when RGB differs a lot (largest: Maersk Blue 313, Modulex Terracotta, Pearl Red 1069, Metallic Silver 80 and Sand Green 378 are the notable ones by weight). Names agree, but the two sites may mean different shades.
- The overrides rest on LEGO colour naming knowledge plus LDConfig comparison, not on Rebrickable's external-id table.
- The code is from the LDConfig of the library you pass in; run the generator with the library version you ship.

Extending: add `"<rebrickable id>": (<ldraw code>, <exact bool>)` to `COLOUR_OVERRIDES` (the script aborts if the code is not in LDConfig), regenerate, and add a spot check in `tests/test_rebrickable_maps.py`. Use `NAME_FIXES` for names that only differ by abbreviation.

## Parts

`part_relationships.csv` types (child_part_num to parent_part_num): P print, T pattern, M mold, A alternate: the parent has the same geometry, so these become aliases. B (sub-part) and R (pair) relate different shapes and are ignored. A part resolves by:

1. identity: `parts/<part_num lowercased>.dat` exists (not listed);
2. relation: follow P, T, M, A child to parent up to 4 hops to the first existing file;
3. suffix: strip LDraw-style `prNNNN` or `patNNNN` and test the base.

Aliases are only emitted when the target file exists, are lowercase, never equal their key. A printed part aliases to its unprinted base: the shape is right, the print is lost.

Coverage of 64,901 Rebrickable parts (there is no popularity column, so this is unweighted):

| resolution | parts | share |
|---|---|---|
| identity | 5,569 | 8.6% |
| alias via relation | 20,582 | 31.7% |
| alias via suffix | 1,079 | 1.7% |
| unresolved | 37,671 | 58.0% |

Of 59,252 Plastic parts, 32,239 are unresolved; Cardboard/Paper (4,177), Cloth (991) and Foam (81) are almost entirely unresolved by design. `no_ldraw` lists the first 300 of 9,837 unresolved Cardboard/Paper, Cloth, Foam and sticker-sheet parts, which LDraw does not model; this is a policy-based statement, not a per-part proof. Unresolved part_cat_ids (names are not in the inputs): 60 (7,650), 17 (5,047), 58 (4,649, mostly sticker sheets), 61 (2,986), 4 (2,884), 65, 57, 41, 66, 63, 75, 78.

Most-referenced unresolved parts (children pointing at them in the relationship table, the best popularity proxy available): 4066 Duplo Brick 1x2x2 (458), minifig hips 970c03 (436) and torsos 973c27h01 (373), 970c27, 973c03h03, 973c01h01, 3814 torso, Modulex tiles 1022A/1021A/1011A, Pen Bead parts penupn0004/0003, 2835. These are minifig torso/leg assemblies (`973cNNhNN`, `970cNN`) that LDraw names differently or models as separate pieces, and non-LDraw systems (Duplo, Modulex, Pen). A future pass could map `970cNN`/`973cNNhNN` to LDraw's assemblies by hand.

Not verifiable offline: whether a part exists in LDraw under an unrelated number (renumbered or stickered variants that Rebrickable does not link), and the real-world popularity of the unresolved parts.

The part counts above are unweighted over all 64.9k Rebrickable part numbers, most of which are rare prints, Duplo, Modulex and stickers. Weighted by `quantity` in Rebrickable's `inventory_parts.csv` (spares excluded; 5,295,735 pieces over 63,150 distinct parts, measured against the committed alias map and LDraw `complete.zip` 2609):

|---|---|---|
| identity (same number exists in LDraw `parts/`) | 94.2% | 8.3% |
| alias | 2.6% | 33.9% |
| unresolved | 3.2% | 57.8% |

- Colour coverage by pieces: 99.75%.
- Of the 500 most-used parts 496 resolve; of the 2000 most-used, 1879.
- Most-used unresolved: `298c02` (4,896), `3711a` (3,717), `970c03` (1,858), `30237b` (1,608), `3046a` (1,234), `1011A` (1,100), `30237a`, `970c28`, `970c27`, `1121L`..`1142L` (Modulex tiles). ## BrickLink colours

`ldraw_tools/data/bricklink-colours.json` maps BrickLink colour ids to LDraw codes for the BrickLink XML/CSV and BrickStore importers and the BrickLink wanted-list export. Rebrickable's bulk `colors.csv` carries no `external_ids`, so the table is built by `tools/build_bricklink_colours.py` from the BrickLink/LDraw pairs of the `legocolors` R package (MIT), then completed by colour name against `rebrickable-colours.json`. Keys: `colours` (id to `{name, ldraw, exact, method}`), `by_name` (normalised name to id, for CSVs that carry names), `reverse` (LDraw code to one BrickLink id, for export) and `unmapped` (ids with no certain LDraw colour: Modulex, Clikits, Neon and similar). An unmapped colour is reported on import and omitted, with the reason, on export; it is never guessed. Part numbers go through the same alias data as the Rebrickable import.
